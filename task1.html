1. Projekta kopsavilkums

Izveidot tīmekļa spēli, kurā lietotājs min cenas reāliem sludinājumiem (galvenokārt no Latvijas sludinājumu vietnēm), iegūst punktus par precizitāti un var sacensties ar draugiem. Spēle ir latviešu valodā, mobilā pirmā, bez reģistrācijas sākumā.

Mērķis nav MVP — uzreiz tiek būvēta ražošanas līmeņa arhitektūra ar PostgreSQL, Go backend, React frontend, Docker izvietošanu uz Hetzner.

2. Arhitektūras kopsavilkums

Lietotājs → Cloudflare (DNS + CDN) → Hetzner VPS
                                    ├── Caddy (HTTPS, reverse proxy, statisko failu apkalpošana)
                                    ├── Go backend (API + WebSocket + viegls SSR SEO vajadzībām)
                                    ├── PostgreSQL 16 + PostGIS (dati + ģeogrāfiskie punkti)
                                    ├── Redis 7 (sesijas, daudzspēlētāju pub/sub)
                                    └── React SPA (Vite būvēti statiskie faili)

Galvenais princips: frontends ir tikai renderēšanas slānis. Visi jutīgie dati (pareizās cenas, precizitātes aprēķini, spēles sesiju stāvoklis) paliek serverī. Frontendā nekas netiek glabāts.

4. Funkcionālās prasības

4.1. Viena spēlētāja režīms (HTTP)

  1. Sākuma ekrāns ar pogu "Spēlēt" un kategoriju izvēli.
  2. Kategoriju izvēle (vismaz 3: Automašīnas, Dzīvokļi, Sadzīves tehnika).
  3. Spēles ekrāns: viens sludinājums (attēls + nosaukums + apraksts) un cenas ievades lauks.
  4. Laika limits: 60 sekundes uz vienu sludinājumu (konfigurējams).
  5. Atbildes iesniegšana ar pogu "Apstiprināt".
  6. Tūlītēja atgriezeniskā saite: pareizā cena, lietotāja minējums, precizitātes procents.
  7. Poga "Tālāk" pāriet uz nākamo sludinājumu.
  8. Pēc 10 sludinājumiem — rezultātu ekrāns ar kopējo precizitāti, labāko un sliktāko minējumu, dalīšanās pogu.

4.2. Precizitātes aprēķins

Formula: precizitāte_% = max(0, 100 - (|minējums - pareizā_cena| / pareizā_cena) * 100)

Kopējais rezultāts: vidējais aritmētiskais no 10 minējumiem.

4.3. Daudzspēlētāju režīms (WebSocket)

  • Istabas izveide ar kodu un saiti.
  • Spēlētāji pievienojas pēc koda.
  • Visi spēlētāji min vienus un tos pašus sludinājumus.
  • Rezultātu ekrāns ar visu spēlētāju ranglistu.
  • WebSocket tiek izmantots tikai daudzspēlētāju režīmā; viena spēlētāja režīmā pietiek ar HTTP.

4.4. Nākotnes funkcijas (nav jābūvē tagad, bet arhitektūra jāatstāj vieta)

  • Iknedēļas ranglists.
  • Lietotāju profili (Supabase auth vai līdzīgi).
  • Karšu skats ar sludinājumu atrašanās vietām (PostGIS dēļ).
  • Iespēja ieteikt sludinājumus.
  • Kategoriju paplašināšana.

5. Datu modelis (PostgreSQL + PostGIS)

5.1. Listing (jautājumu banka)

CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE listings (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    category      TEXT NOT NULL,
    title         TEXT NOT NULL,
    description   TEXT,
    image_url     TEXT NOT NULL,
    actual_price  NUMERIC(12,2) NOT NULL,
    currency      TEXT NOT NULL DEFAULT 'EUR',
    source_url    TEXT,
    location      GEOGRAPHY(POINT, 4326),
    region        TEXT,
    is_active     BOOLEAN NOT NULL DEFAULT TRUE,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_listings_location ON listings USING GIST (location);
CREATE INDEX idx_listings_category ON listings (category) WHERE is_active;
Kritiski: actual_price nedrīkst nonākt API atbildē pirms lietotāja iesniegšanas.

5.2. GameSession un Guess

CREATE TABLE game_sessions (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    mode          TEXT NOT NULL,
    category      TEXT NOT NULL,
    listing_ids   UUID[] NOT NULL,
    current_index INT NOT NULL DEFAULT 0,
    status        TEXT NOT NULL DEFAULT 'active',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE guesses (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_id   UUID NOT NULL REFERENCES game_sessions(id),
    listing_id   UUID NOT NULL REFERENCES listings(id),
    player_id    TEXT,
    guess_value  NUMERIC(12,2) NOT NULL,
    accuracy     NUMERIC(5,2) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

Precizitāte tiek aprēķināta serverī, frontendam tikai nolasāma.

6. API specifikācija

6.1. Viena spēlētāja režīms (HTTP)

Metode Ceļš Funkcija
POST /api/game/single/start Izveido sesiju, atgriež sessionId + pirmo jautājumu (bez cenas)
POST /api/game/single/guess Iesniedz minējumu, atgriež pareizo cenu un precizitāti
POST /api/game/single/next Pāriet uz nākamo jautājumu, atgriež nākamo jautājumu (bez cenas)
POST /api/game/single/finish Pabeidz, atgriež kopsavilkumu

Visas atbildes nekad nesatur pareizo cenu pirms iesniegšanas.

6.2. Daudzspēlētāju režīms (HTTP + WebSocket)

HTTP daļa:

  • POST /api/game/multi/create — izveido istabu, atgriež roomCode un saiti.
  • POST /api/game/multi/join — pievienojas istabai pēc koda.

WebSocket notikumi (Socket.IO vai gorilla/websocket ar līdzīgu protokolu):

Virziens Notikums Dati
Client→Server room:ready Sagatavots
Server→Client room:players Spēlētāju saraksts
Server→Client game:start Sākas spēle
Server→Client game:question Jautājums (bez cenas)
Client→Server game:guess { listingId, guessValue }
Server→Client game:guess:result { playerId, actualPrice, accuracy }
Server→Client game:scoreboard Pašreizējie rezultāti
Server→Client game:finished Galīgais rangs

WebSocket autentifikācija: pievienojoties istabai, jāpārbauda derīgs roomCode + parakstīts spēlētāja tokens.

7. Frontend prasības

7.1. Ekrāni

  1. Sākums — liela poga "Spēlēt", kategoriju kartītes.
  2. Spēle — attēls, nosaukums, apraksts, cenas ievades lauks, taimeris, poga "Apstiprināt".
  3. Atgriezeniskā saite — pārklājums ar pareizo cenu, minējumu, precizitāti, poga "Tālāk".
  4. Rezultāti — liels precizitātes %, sadalījums, poga "Spēlēt vēlreiz" un "Dalīties".

7.2. Dizaina principi

  • Mobilā pirmā.
  • Lieli pieskāriena mērķi (min 44×44 px).
  • Latviešu valoda UI tekstos.
  • Vienkāršs, spēlīgs dizains.
  • Kontrasts atbilst WCAG AA.

7.3. SEO risinājums (nākotnei)

Frontends ir React SPA, bet Go serveris pirms statiskā faila atgriešanas veic vieglu SSR:

  • index.html satur meta tagu vietturus (__TITLE__, __DESCRIPTION__).
  • Go pēc pieprasījuma ceļa aizstāj vietturus ar attiecīgās lapas saturu.
  • Ja nākotnē nepieciešams indeksēt daudz satura lapu, var pievienot atsevišķu Next.js pakalpojumu tikai SEO lapām, nemainot React SPA.

8. Izvietošana (Docker Compose uz Hetzner)

8.1. Pakalpojumi docker-compose.yml

  • caddy — HTTPS, reverse proxy, statisko failu apkalpošana. Publicē tikai 80/443.
  • backend — Go API + WebSocket + viegls SSR.
  • postgres — PostgreSQL 16 ar PostGIS paplašinājumu (izmantot postgis/postgis attēlu).
  • redis — Redis 7.
  • frontend — React būvētie statiskie faili (var būt Caddy sējumā vai atsevišķā attēlā).

Postgres un Redis darbojas tikai iekšējā Docker tīklā, nav pakļauti publiskajam tīklam.

8.2. Izvietošanas soļi

  1. Servera inicializācija: Ubuntu 24.04 LTS, SSH atslēga, Hetzner Cloud Firewall atļauj tikai 22 (ierobežots ar IP), 80, 443.
  2. Instalē Docker + Compose plugin no Docker oficiālā repozitorija.
  3. Klonē repozitoriju, izveido .env (Postgres parole, Redis parole, AUTH_SECRET utt., ģenerē ar openssl rand -hex 32).
  4. docker compose up -d, pārbaudi veselību.
  5. Rezerves kopijas: pg_dump cron.

9. Drošības prasības

  • Pareizā cena nekad neparādās frontendā pirms iesniegšanas.
  • API ātruma ierobežošana uz /api/guess un istabas izveides endpointiem pēc IP.
  • Postgres nepieejams no ārpuses.
  • WebSocket autentifikācija ar parakstītu tokenu.
  • Docker publicētie porti var apiet ufw — tikai Caddy publicē 80/443.
  • Žurnāli un veselības pārbaudes endpointi.
  • Ja saglabā precīzas koordinātas, jāpievieno nejauša nobīde (piem., 500 m) privātuma aizsardzībai.

10. Izstrādes secība

Posms Saturs Aptuvenais laiks
1 Hetzner serveris + Docker + Caddy + Postgres + Redis darbība 1 diena
2 PostgreSQL shēma + PostGIS + sqlc ģenerēšana + sēklas dati (50–100 jautājumi) 1–2 dienas
3 Go viena spēlētāja API (start/guess/next/finish) + React SPA lapa 3–5 dienas
4 Go WebSocket serveris + istabu loģika + sinhronizācija 5–7 dienas
5 Rezultātu kopsavilkums, kopīgošanas karte, atkārtota spēlēšana 2 dienas
6 SEO viegls SSR (meta tagu vietturi) 1 diena
7 Drošības sacietēšana, žurnāli, rezerves kopijas 1–2 dienas

Kopā aptuveni 2–3 nedēļas atkarībā no ikdienas laika ieguldījuma.

11. Atlikušie lēmumi, kas jāapstiprina izstrādes laikā

  1. Vai daudzspēlētāju režīms ir obligāts pirmajā versijā? Ja nē, vispirms viena spēlētāja pilnā plūsma, WebSocket otrajā iterācijā.
  2. Vai Redis tiek izmantots no sākuma? Ieteicams jā, lai vēlāk būtu vieglāk paplašināt.
  3. Vai izmanto Prisma vai sqlc? Izvēlēts sqlc (tipu drošība, nav ORM ierobežojumu PostGIS funkcijām).
  4. Vai Go maršrutēšanai izmanto chi vai gin? Abi der, chi ir vieglāks.
  5. Vai frontend statiskos failus apkalpo Caddy vai Go? Caddy ir vienkāršāk.

12. Kritiski svarīgas piezīmes

  • Cenas godīgums: ja cena ir klienta JSON failā, lietotājs to var izlasīt. Tāpēc cena glabājas tikai PostgreSQL un tiek atgriezta tikai pēc minējuma iesniegšanas.
  • Attēlu autortiesības: ja ņem ss.lv attēlus, tie pieder sludinājumu autoriem. Publiskā produktā labāk prasīt atļauju vai izmantot savus attēlus.
  • ss.lv scraping: ja automātiski velk sludinājumus, jāpārbauda ss.lv lietošanas noteikumi. Drošāk — manuāli pievienot sludinājumus.
  • GDPR: ja vāc lietotāju datus (vārdus ranglistam), vajag privātuma politiku. Sākumā izmantot anonīmus ID.
  • PostGIS: izmantot GEOGRAPHY (nevis GEOMETRY) un SRID 4326. GIST indekss ir obligāts telpiskajiem vaicājumiem.
  • Ģeokodēšana: adrese → koordinātas jāveic kā fona uzdevums, nevis sinhroni API pieprasījumā. Var izmantot Nominatim (OpenStreetMap) vai komerciālos pakalpojumus.
